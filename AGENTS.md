# Project instructions

## Визуальные изменения

1. До реализации сформулируй наблюдаемые критерии результата из запроса пользователя. Не подменяй их удобными техническими показателями.
2. После реализации сравни референс и фактическую игру при сопоставимом масштабе. Проверь общий кадр и проблемный участок крупно; для движения — полный цикл.
3. Отдельным проходом ищи причины отклонить собственный результат: перекрытия, разрывы, неверную перспективу, скольжение, потерю читаемости.
4. Для каждого критерия укажи фактическое подтверждение либо оставшееся расхождение. Успешные тесты сами по себе не подтверждают визуальное соответствие.
5. Новая проверка исправления должна обнаруживать известный плохой вариант. Не ослабляй критерий ради прохождения текущей реализации.
6. Сообщай «исправлено» только после проверки запрошенного поведения. Если проверка неполная — прямо обозначь её границы.
7. Кадры для сравнения снимай из самой игры (`tools/capture-organic-world.cjs`), открывай их и прикладывай к отчёту пути к кадрам «до» и «после». Без приложенных кадров визуальная работа не считается проверенной.
8. Одна визуальная проблема — одна итерация: не смешивай несколько исправлений в одной проверке.

Для проходов проверяй непрерывный свободный подход всей ширины маршрута через всю глубину препятствия. Наличие нужного цвета или свободной точки в конце маршрута не доказывает проходимость подхода.

Правила читаемости — проверяются при любом визуальном изменении, даже если пользователь о них не просил:
- враги и башни — самые контрастные элементы кадра; в кадре в оттенках серого они остаются различимыми;
- у всех объектов карты один ракурс камеры — как у площадок под башни.

Границы: визуальная работа не меняет функции боя, баланс, `PATH`, `GATE_D` и позиции площадок без явного разрешения пользователя. Если такое изменение разрешено — назови его отдельно в описании PR. Тяжёлые этюды и черновые рендеры не коммить в репозиторий, только итоговые ассеты.

Браузер с диска: игра открывается двойным кликом по `prototype/index.html` (`file://`). В этом режиме картинки «чужого происхождения», и любое чтение пикселей из холста с ними (`getImageData`, `toDataURL`) бросает SecurityError. Такое чтение — только в `try/catch` с запасным путём без пикселей. Съёмка кадров через Node этого не ловит, поэтому после правок отрисовки открыть игру с диска в браузере и проверить консоль.

Имена ассетов: если у атласа или картинки меняется размер или раскладка, у файла меняется имя (`-v2`), иначе кэш браузера подставит старую картинку и игра сломается у всех, кто уже открывал её.

Ревью: визуальный PR не вливается без второго взгляда на приложенные кадры — другой сессией, другим агентом или человеком.

## Кто запускает проверки

По договорённости с пользователем тесты, съёмку кадров и браузерные проверки запускает пользователь, чтобы экономить токены. Агент готовит изменения, необходимые проверки и точные команды из корня репозитория, разбирает присланные результаты и исправляет ошибки. Самостоятельно запускать проверки — только по явной просьбе пользователя.

Это правило определяет исполнителя проверок выше, но не отменяет критерии качества. В отчёте и чекпоинте различай результаты, подтверждённые пользователем, ранее выполненные проверки и ещё не проверенное. Не объявляй тесты зелёными или визуальную работу проверенной без фактических результатов и кадров.

## Чекпоинты

При изменении симуляции — `node tools/restamp-replays.cjs --write`; никаких исключений для старых отпечатков в валидаторе. Если строгая проверка реплеев не проходит, выясни причину, не подменяй записанные результаты ради прохождения.

После существенных этапов сохраняй промежуточные коммиты и поддерживай `reports/ACTIVE-WORK-CHECKPOINT.md`: текущее состояние, проверенные результаты, известные дефекты и следующий шаг. Не переноси неподтверждённые выводы в статус завершённой работы.
